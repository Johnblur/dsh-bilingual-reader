# dsh-bilingual-reader — 领域化翻译 Agent 方案研究（讨论稿）

> 状态：方案研究，未动代码
> 范围：把翻译器从"无状态 workflow"升级为"有领域感知、可积累、可自我优化"的 agent。
> 本文档只记录**已确认可写**的两件事（领域识别、领域信号兜底）；**领域术语表**因领域存在包含关系、数据结构未定，单独在 §3 深入讨论（先不落地）。

---

## 0. 背景与目标

现状是一个**无状态 workflow**：每篇 PDF 独立抽取临时术语 → 独立翻译 → 结果丢弃。没有领域概念、没有跨论文积累、不会自我改进。

目标（三步）：
1. **领域识别**：知道这是哪类论文（ML / 生物 / 物理…）。
2. ~~领域术语表：一个领域一套积累的术语→译法映射，跨论文复用。~~ ← **数据结构未定，见 §3，先不写入方案**
3. **领域信号兜底**：上下文匹配失败时，用【领域 + 领域术语】辅助翻译，而非匹配错误的上下文或裸译。

> 注：本文只固定 1、3 的实现方向。2 用"待定"标注，等数据结构讨论定稿再补。

## 1. 领域识别（已确认方向）

### 1.1 为什么值得做
当划词内容在全文**无法唯一匹配**（短词、多义词、词形/断词差异）时，知道文章属于哪个领域，能让模型靠"领域常识 + 专业术语"去正确理解，而不是：
- 匹配一个可能错误的上下文（更糟）；或
- 完全无上下文裸译（质量差）。

领域是翻译的"先验知识"，正是 agent 区别于 workflow 的关键。

### 1.2 识别来源（逐级降级）
- **用户显式选择**（UI 下拉）——最可靠。
- **LLM 识别**（推荐为主）——用论文标题 + 摘要（或全文开头若干字）做一次轻量调用，输出领域标签。一次调用、准确、零人工。
- **启发式兜底**——按关键词命中率（transformer/neural→ML；protein/cell→bio；…）。零成本，粗糙。

结果写入**文档元数据**，进入翻译请求，供提示词与术语路由使用。

### 1.3 建议
- 领域下拉 = `自动识别 + 预设领域 + 自定义领域`。
- 默认 `自动`（LLM 判一次）；用户可手动锁定某领域。
- 文档→领域映射按文件 hash 记忆，重开记住。

## 2. 领域信号兜底（已确认方向）

### 2.1 问题
当前 `doTranslate` 用 `normDoc.indexOf(selText)` 找**唯一**位置：
- 短词多处出现 → `hits.length > 1` → 直接放弃，无上下文直译。
- 词形/断词不一致（连字符、大小写、单复数、PDF 断行）→ 精确子串 miss。

### 2.2 方案：上下文缺失时，用"领域信号"顶替
当 `hits.length !== 1`（匹配失败）时：
- **不**喂可能的错误上下文；
- 改为向提示词注入 **领域信号**：`【所属领域】machine learning` + 该领域的术语；
- 模型靠"领域 + 术语"理解，而非裸译或错误上下文。

这比"无上下文直译"强，也比"错误上下文"安全。

### 2.3 提示词形态（示意）
```
你是学术论文翻译助手。请结合领域知识理解以下内容。
【所属领域】machine learning
【领域术语】attention=注意力机制; loss=损失; ...
把选中片段译成<目标>。只输出译文，不要解释。
```
领域信号来自 §1 的识别结果 + §3 的术语表（待定）。

## 3. 【待定】领域术语表 — 数据结构开放设计

> 这是本方案最需要先定的一件事，暂不写进落地。核心难点见下。

### 3.1 核心难点：领域不是平铺列表，而是有包含关系

你提出的关键洞察：**子学科必然使用父学科的术语**；同一个父学科下平行的子学科各有其**专有术语**。

例子（ML 领域）：
```
ML
├── NLP      （用到 ML 全部术语 + 自己的 transformer, BERT, tokenizer…）
├── CV       （用到 ML 全部术语 + 自己的 convolution, IoU, backbone…）
└── RL       （用到 ML 全部术语 + 自己的 policy, reward, agent…）
```

所以领域之间是**树（或图）**，术语表**必然不是一张表**——必须支持"沿领域层级向上合并继承"。

### 3.2 候选数据结构

**方案 A：树 + 每节点一张术语表，查找沿祖先链合并**
```
Root
└── ML
    ├── NLP { "transformer":"Transformer", "token":"词元", ... }
    ├── CV  { "backbone":"骨干网络", "IoU":"交并比", ... }
    └── RL  { "policy":"策略", "reward":"奖励", ... }
```
- 查找 `NLP` 领域术语 = 合并 `Root → ML → NLP` 三节点表。
- 子节点同名术语**覆盖**父节点（越具体越准）。
- 优点：直观、符合"父术语共享、子术语专有"。
- 缺点：需维护一棵树；多父/交叉学科（如 `biomedical NLP` 同时是 bio 和 NLP）会打破严格树。

**方案 B：扁平术语表 + 每术语带所属领域标签，查找按"目标领域 + 祖先链"过滤**
```
[ { term:"transformer",       domain:["NLP","ML"],      zh:"Transformer" },
  { term:"policy",             domain:["RL","ML"],       zh:"策略" },
  { term:"genome",             domain:["bio"],           zh:"基因组" } ]
```
- 查找 `NLP` = 取所有 `domain` 含 `NLP` 或 `NLP` 任意祖先（ML/Root）的条目。
- 一个术语可标多个领域（天然支持交叉学科）。
- 优点：灵活、支持多父；术语表是可"平铺管理"的资产。
- 缺点：领域层级关系需要另存一张"领域关系图"；同名术语在不同领域可能有不同译法（需按领域区分）。

**方案 C：有向无环图（DAG）**——兼有树继承 + 交叉学科，但查找/合并逻辑最复杂。

### 3.3 定稿（基于已确认决策）
**方案 B：扁平术语表 + domain 数组 + 一张独立的领域关系图**，术语条目用**多语种平级的富对象**。

#### 3.3.1 数据结构核心原则
1. **领域关系**单独一张图（树/DAG），**不嵌进术语条目**——两者解耦，各自演进（领域分类会变，术语资产要能跨分类复用）。
2. **术语条目是扁平可平铺的资产**（可导入导出、可统计、可跨领域）。
3. **多语种平级**：`term` 不默认英语。一个术语条目里，各语种是**并列字段**，避免"不同目标语言要维护不同术语表"。
4. **同形异义拆成不同条目**（见 3.3.3）——这是满足"锁定 domain 时唯一"的关键机制。
5. 富对象带元数据（来源/置信度/用户确认/首次出现），支撑自我优化 + 防错误放大。

#### 3.3.2 术语条目（富对象 · 多语种平级）
```jsonc
{
  "id": "t_cell_bio",                       // 稳定 id
  "domains": ["biology"],                    // 所属领域（可多个；空数组=通用兜底）
  "terms": {                                 // 多语种平级，不默认英文
    "en": "cell",
    "zh": "细胞",
    "ja": "細胞",
    "prompt": "cell"                         // 给模型的统一指代（可用 en 或任一）
  },
  "confidence": 0.9,                         // 置信度：低则不自动沉淀
  "confirmedByUser": false,                  // 是否经用户确认（防错误放大）
  "source": "llm" | "user" | "seed",         // 来源
  "firstSeen": 1724800000                    // 首次出现
}
```

#### 3.3.3 同形异义（跨领域译法不同）——靠拆条目 + domain 限定
`cell` 在生物学=细胞、在神经网络=单元：**这视为两个不同概念**（语义不同，仅英文词形相同），拆成两条：
```jsonc
{ "id":"t_cell_bio", "domains":["biology"], "terms":{"en":"cell","zh":"细胞"} }
{ "id":"t_cell_cv",  "domains":["computer-vision","deep-learning"], "terms":{"en":"cell","zh":"单元"} }
```
- 检索 `domain=biology, en=cell` → 唯一命中第一条 → `zh=细胞`。
- 检索 `domain=computer-vision, en=cell` → 命中第二条 → `zh=单元`。
- **满足约束**：锁定一个 domain 时，该术语在每种语言下的表达唯一（不同语义已用不同条目分开）。

#### 3.3.4 检索与合并算法（给定目标领域 D + 源语言 S + 查询词 q）
1. 沿领域关系图求 `D` 的**祖先闭包** `A(D)`（D 自身 + 所有祖先，因为子领域继承父领域术语）。
2. 过滤：术语条目 `domains ∩ A(D) ≠ ∅` **且** `terms[S]` 命中 `q`（或模糊命中）。
3. 若有多个命中且不同译法，取**领域最近**（`domains` 里直接含 D 者优先；其次近祖先）。
4. 返回该条目 `terms[T]` 作为目标语言译法；若无术语则回退为裸词。
5. **特殊**：`domains` 为空数组的条目视作**通用兜底**，任何领域都可继承。

> 命中判定用 `terms[S]` 语言对齐，不把 `term` 当英语——日语原文时 `S=ja`，查 `terms.ja`。

#### 3.3.5 领域关系图（独立于术语表，定稿为 DAG）
```jsonc
// domain-graph.json — 分层分类，与术语表解耦。有向无环图（DAG），允许一节点多父。
{
  "roots": ["computer-science", "biology"],           // 可有多个根
  "edges": {                                           // 父 → 子 的有向边
    "computer-science": ["machine-learning", "computer-vision", "nlp"],
    "machine-learning": ["deep-learning", "reinforcement-learning"],
    "deep-learning": ["nlp", "computer-vision"],       // nlp/cv 多父：交叉学科用 DAG 表达
    "biology": ["bioinformatics"],
    "bioinformatics": ["machine-learning"]             // 交叉：bioinformatics 也是 ML 子节点
  }
}
```
- **已定：用 DAG**（工科交叉多，`nlp` 同时是 ML 与 deep-learning 子节点、`bioinformatics` 也是 ML 子节点，均可用多父表达）。
- 查询给定节点 D 时，求**祖先闭包** `A(D)`（沿反向边向上遍历，含自身）——`terms.domains ∩ A(D) ≠ ∅` 即命中（子领域继承父领域术语）。
- DAG 需**无环校验**（录入/加载时检测，防循环导致祖先闭包死循环）；祖先闭包可用 BFS/DFS + visited 集合实现，避免重复访问。
- 术语表 `domains` 引用这里的节点 id。

### 3.4 数据结构相关的遗留问题
1. **领域关系图用树还是 DAG？** ~~已倾向 DAG~~ → **已定：DAG**（见 §3.3.5），需实现无环校验 + visited 集合的祖先闭包。
2. **术语条目 `terms` 是否用"语言"还是"语言+地区"（zh-cn/zh-tw）？** 目前用语言码（zh），若需细分可扩展。
3. **"领域锁定唯一"的边界**：同一个 (D,S,q) 理论唯一；但若两条术语条目 `domains` 都含 D 且 `terms.en` 都命中 q（数据矛盾/用户误录），需要**冲突解决策略**（置信度优先 / 最近领域优先 / 报错提示用户）。应保证录入时校验。

### 3.5 已定决策（本轮确认）
- **存储位置：宿主文件系统**（非 localStorage）。术语表/领域资产存到宿主工作区文件（`~/.dsh/profiles/<profile>/` 或插件指定目录），可携带、可备份、可分享，真正"资产化"。host 需加读写文件路由。
- **种子术语表：需要**（首装即让翻译质量稳定）。但**种子如何获取**待讨论（见 §3.4 遗留 + §7），可选来源：LLM 离线批量预生成、内置打包、用户导入。

## 3.6 术语注入链路（具体实现方案，可讨论）

> 术语要真正发挥作用，必须在**翻译前**把【领域术语】注入提示词。当前 `glossaryNote` 只注入"当前文档临时抽取的术语"，需改为**从领域术语表查询**。这是一条独立的调用链路，单独写下便于讨论。

### 3.6.1 链路全貌（一次划词翻译）
```
[client] 选中/复制文本
   │
   ▼
[client] 1. 确定领域 D（用户选择 or LLM 识别，见 §1）
   │ 2. 确定源语言 S / 目标语言 T（多语种，见 lang.ts）
   │
   ▼
[client] 3. 调 host:  query-terms(D, S, 文本/关键词)
   │        └→ host 沿领域关系图求祖先闭包 A(D)
   │           └→ 过滤术语表 domains∩A(D)≠∅ 且 terms[S] 命中
   │           └→ 返回 [{ term, terms[T] 译法, confidence, ... }]
   │
   ▼
[client] 4. 调 host:  translate(selection, { D, S, T, terms })
   │        └→ host 把 terms 拼进提示词 glossaryNote
   ▼
[client] 5. 展示译文 + 实际用的领域/术语信号（见 §5）
```

### 3.6.2 host 新路由（草案）
- `POST /bilingual-reader/query-terms`：入参 `{ domain, sourceLang, text }`，返回命中术语列表（`[{ term, translation, confidence, confirmed }]`）。内部沿领域图求祖先闭包、过滤术语表。
- （复用）`POST /bilingual-reader/translate-selection`：入参加 `{ domain, terms? }`，host 注入提示词。
- （新增读写）术语表/领域图存取路由：`GET/POST /bilingual-reader/terms`、`/bilingual-reader/domain-graph`（宿主文件读写，见 §4）。

### 3.6.3 术语注入粒度（已定：混合）
- **A 命中式**：只注入与划词文本**实际匹配**的术语（精准、省 token——主路径）。
- **B 领域全量式**：注入当前领域区间的**整个术语表**（覆盖面广，但 token 多、可能引入噪声——兜底路径）。
- **已定：混合** —— `A 为主、B 兜底`：
  - 划词**能匹配**到术语 → 用 A（只注入命中的那几条，精准省 token）。
  - 划词**短/匹配失败/上下文缺失** → 用 B（注入当前领域的术语表兜底——正是"上下文缺失时用领域信号"的场景）。
  - 实施上用阈值判定：命中集为空或文本过短时切到 B。
- 触发 B 时标注"已注入领域术语 N 条"，便于 UI 显示实际信号（见 §5）。

### 3.6.4 依赖关系
- 领域术语表查询依赖**领域识别**（§1）先给出 D。
- 注入依赖**术语表结构**（§3.3 已定稿）。
- 与**多语种**（现有 `lang.ts`）联动：`S/T` 来自源/目标语言下拉，术语查询用 `terms[S]` 对齐。

## 4. 数据模型（除术语表外）

| 数据 | 存哪 | 说明 |

## 5. UI 增量（定稿：弹层承载管理 + 诊断条折叠）

底部区重排为三区块，解决"内容多、位置挤"：

```
① 配置行（一行）
   [✓已启用自动翻译|翻译选中]  源▾ 目标▾ 领域▾  [上下文 ——○—— 100字]  [⚙ 术语/领域]
② 诊断条（一行小字，click 展开；有异常默认展开）
   识别为中文 · 领域深度学习 · 已匹配上下文
   （点开显示完整状态 + 术语冲突详情）
③ 结果区（主要展示）
   [匹配状态 ✓/⚠]  原文：...  译文：...  [复制译文]
```

### 5.1 ① 配置行
- 保留：`[✓已启用自动翻译]`（desktop）/ `[翻译选中]`（web，自动不可用）——**放原位置（行首）**。
- 源 / 目标 / 领域 下拉 + 上下文滑块，现有不动。
- 新增：行尾 `⚙ 术语/领域` 图标按钮 → 打开术语管理弹层。

### 5.2 ② 诊断条（新增，click 展开）
- 把原**四行状态**（识别为 / LLM 判断领域 / 术语警告 / 匹配状态 ✓/⚠）收敛为**一行诊断**：
  `识别为中文 · 领域深度学习 · 已匹配上下文`（灰字小号，`·` 分隔）。
- **click 展开**完整详情（状态解释 + 术语冲突完整警告）。
- **有异常（如术语冲突）时默认展开**，且该行变 ⚠ 色——dev 阶段便于看到完整信息。

### 5.3 ③ 结果区（保持）
- 匹配状态、原文（可折叠）、译文 + 复制按钮，不变。

### 5.4 术语/领域管理窗口（阶段2.1 · 只做查看）——承载方式待定，倾向独立窗口
- **问题**：better-sidebar 面板细长，不适合放 术语表列表 + 领域图。期望一个**真正独立的窗口**来承载。
- **现状**：better-sidebar 有**自由窗口（float / free window）**能力（`floatTab(state, tabId, x, y)` reducer + `FloatWindow {id,tab,x,y,w,h}`），**但 `BetterSidebarService` 接口未暴露**，插件无法用代码主动弹出 float 窗口（只能靠用户手动拖拽 tab 出侧栏）。也**没有**对外开放的 modal/抽屉 API。
- **结论**：要独立窗口，需给 better-sidebar 提 feature PR，新增"插件主动 float"的公开 API（见 §5.6）。**待 issue/PR**；在 better-sidebar 支持前，保留"侧栏内查看"为过渡方案。
- **阶段2.1 只做查看**：术语表（按领域过滤：源词/译法/领域/置信/是否确认/来源）+ 领域图（DAG 节点+父子）。

### 5.6 【待提 PR】给 better-sidebar 的 "插件主动 float 窗口" 能力草案
- **需求**：`BetterSidebarService` 增加公开方法，让外部插件能主动把某个 tab 弹为自由窗口（独立窗口），而不是只能靠用户手动拖拽。
- **已有基础**：`state.ts` 的 `floatTab(state, tabId, x, y)` reducer + `<Store>`/`SidebarStore` 已能操作 `floats`；只差在服务接口上开一个方法。
- **建议 API（草案）**：
  ```ts
  /** 把 tab 弹为自由窗口（独立窗）。seed 可含 tab id / 类型 / 尺寸 / 初始坐标。 */
  floatTab(tabId: string, opts?: { x?: number; y?: number; w?: number; h?: number }): void;
  // 或形式二：floatOpen(seed, opts?) 用 tab descriptor 打开并直接浮动。
  ```
- **语义**：应复用现有 `floatTab` reducer；`w/h` 有默认（如 390×780，契合现有 float 默认）；坐标默认居中；在 `features` 里加 `'floatWindows'`（已有）或新增 `'floatProgrammatic'` 能力标记。
- **改测点**：`BetterSidebarService` 类型、`service.ts` 实现、单测（float 能力在已启用时可用）、文档。
- **好处**：不只术语/领域管理，任何插件想要"独立查看窗"都能用；且带动 DSH 生态的独立窗能力。
- **可顺带**：提供 `openTab(seed, { float: true })` 或 `openTabInFloat(...)`，语义更直接。

> 注：这是**给 upstream (omdsh-dev/DSH-better-sidebar) 的 feature PR 建议**。在你提 issue/PR 前，可先把这些字段/能力描述整理好。

## 7. 关键风险/取舍（待确认）

1. **自我强化风险**：模型译错 → 术语表沉淀错 → 下次继续错（错误放大）。缓解：沉淀需**用户确认**，或**低置信度不自动沉淀**（富对象字段已支持）。
2. **领域粒度**：粗粒度（ML/bio/physics）够用，还是细分（NLP/CV）？粒度过细术语表稀疏。（术语表 `domains` 已支持一术语多领域，可兼顾。）
3. **领域开放性**：固定枚举（预设+自定义）还是完全开放（模型自由输出标签）？开放灵活但命名空间易碎片化。
4. **种子术语表如何获取**：可选——LLM 离线批量预生成（质量可控但需成本/维护）、内置打包少量常见领域种子、用户导入社区包。**待讨论**（已确认"需要种子"，来源未定）。
5. **语言范围**：术语表**多语种平级**（`terms` 字段，见 §3.3.2），不限于英→中；首期可优先补足英→中质量，其余语种按需扩展。
